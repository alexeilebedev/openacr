## amc Reftype - index
<a href="#amc-reftype"></a>

Every field in a ctype has a **reftype** — a type constructor that
decides what code amc generates for the field.  36 reftypes are
defined in `ssimfile:dmmeta.reftype`.

A field is declared like this:

    dmmeta.field  field:amc.FDb.ind_ns        arg:amc.FNs           reftype:Thash   dflt:""  comment:""
    dmmeta.field  field:dmmeta.Field.field    arg:algo.Smallstr100  reftype:Val     dflt:""  comment:""

The tables below group the reftypes by what they are for, and each entry links to
that reftype's own page.  A reftype page gives the full template: flags from
`dmmeta.reftype`, ssim inputs you need to define, variants and options, the table
of generated functions, the memory model, cross-reference behaviour, and
pitfalls.

A field of a protocol namespace has no reftype page to reach, because a protocol
namespace has no in-memory state at all -- see
[Protocols](/txt/exe/amc/proto.md).

### Field name prefixes
<a href="#field-name-prefixes"></a>

Nine reftypes constrain what a field of that reftype may be named.  The
`dmmeta.fprefix` table pairs a prefix — the part of the field name up to
the first underscore — with a reftype, and `amc` checks every field
against it.  A field whose reftype has any `require:Y` pairing must use
one of that reftype's registered prefixes; a field that does not is reported
as `amc.bad_prefix` and fails the run.  (A namespace with a `dmmeta.nsjs` row is exempt, since
the TypeScript projection has no prefix convention.)

The prefix is also how `acr_ed` infers a reftype from a field name you
type.  At most one reftype per prefix may be marked `dflt:Y` — that is the
one inferred; the others must be named explicitly.  `Llist` is the
extreme case: eight prefixes select the eight list shapes, so renaming a
field from `zs_` to `cd_` converts a zero-terminated singly-linked list
into a circular doubly-linked one.

|Prefix|Reftype|Required|Inferred|Meaning|
|---|---|---|---|---|
|`bh_`|[Bheap](/txt/exe/amc/reftype/Bheap.md)|Y|Y|Binary heap|
|`c_`|[Ptrary](/txt/exe/amc/reftype/Ptrary.md)|Y|Y|Pointer array|
|`c_`|[Delptr](/txt/exe/amc/reftype/Delptr.md)|N|N|Owned pointer; permitted, not required|
|`c_`, `p_`|[Ptr](/txt/exe/amc/reftype/Ptr.md)|N|N|Pointer; permitted, not required|
|`cd_`, `cdl_`, `cs_`, `csl_`, `zd_`, `zdl_`, `zs_`, `zsl_`|[Llist](/txt/exe/amc/reftype/Llist.md)|Y|Y|Circular or zero-terminated, doubly or singly linked, FIFO or LIFO|
|`cnt_`|[Count](/txt/exe/amc/reftype/Count.md)|Y|Y|Count of items|
|`ind_`|[Thash](/txt/exe/amc/reftype/Thash.md)|Y|Y|Hash index|
|`ind_`|[Blkhash](/txt/exe/amc/reftype/Blkhash.md)|Y|N|Block hash index|
|`p_`|[Upptr](/txt/exe/amc/reftype/Upptr.md)|Y|Y|Up-pointer|
|`tr_`|[Atree](/txt/exe/amc/reftype/Atree.md)|Y|Y|AVL tree|
|`zs_`|[ZSListMT](/txt/exe/amc/reftype/ZSListMT.md)|Y|N|Zero-terminated singly linked list with atomic head|

Every other reftype places no constraint on the field name.  The live
table is `acr fprefix`.

### Cursors
<a href="#cursors"></a>

A cursor is how generated code iterates a field that holds more than one
element.  amc emits it as a struct named `<Parname>_<name>_<curstype>`
plus four functions — `_Reset`, `_ValidQ`, `_Next`, `_Access` — which the
`ind_beg` / `ind_end` macros drive:

```c++
ind_beg(amc::_db_ctype_curs, ctype, amc::_db) {
    prlog(ctype.ctype);
} ind_end;
```

Ten reftypes have cursors, and three of those offer a second cursor with
different semantics; the `Bitset` option tclass has one too.  A cursor is a
tfunc like any other, so its name is `<Tclass>.<curstype>` and the
generated type ends in that curstype.

Not every cursor is generated by default.  `amcdb.tcurs` carries a `dflt`
flag per cursor: `dflt:Y` means every field of that reftype gets the
cursor, and `dflt:N` means the field must ask for it with a
`dmmeta.fcurs` row naming the field and the curstype.

```ssim
dmmeta.fcurs  fcurs:acr.FDb.zd_all_selrec/delcurs  comment:""
```

|Cursor|Reftype|Default|What it walks|
|---|---|---|---|
|`curs`|[Atree](/txt/exe/amc/reftype/Atree.md)|Y|In-order traversal of the tree|
|`curs`|[Bheap](/txt/exe/amc/reftype/Bheap.md)|Y|Pops the heap in sorted order — destructive|
|`unordcurs`|[Bheap](/txt/exe/amc/reftype/Bheap.md)|N|The underlying array, arbitrary order, non-destructive|
|`curs`|[Blkhash](/txt/exe/amc/reftype/Blkhash.md)|N|Each bucket's blocks, each block's occupied slots|
|`curs`|[Inlary](/txt/exe/amc/reftype/Inlary.md)|Y|The inline elements in order|
|`curs`|[Lary](/txt/exe/amc/reftype/Lary.md)|Y|Every level, in insertion order|
|`curs`|[Llist](/txt/exe/amc/reftype/Llist.md)|Y|The list from head to tail|
|`delcurs`|[Llist](/txt/exe/amc/reftype/Llist.md)|N|Same order, but the current row may be removed inside the loop|
|`curs`|[Ptrary](/txt/exe/amc/reftype/Ptrary.md)|Y|The pointer array in order|
|`oncecurs`|[Ptrary](/txt/exe/amc/reftype/Ptrary.md)|N|Drains the array: `Reset` captures the elements and empties it|
|`curs`|[Tary](/txt/exe/amc/reftype/Tary.md)|Y|The array in order|
|`curs`|[Thash](/txt/exe/amc/reftype/Thash.md)|N|Each bucket head-to-tail; no key order|
|`curs`|[Varlen](/txt/exe/amc/reftype/Varlen.md)|Y|The trailing array|
|`bitcurs`|[Bitsets](/txt/exe/amc/bitset.md)|N|The indexes of the set bits|

The general rule for mutation inside a cursor loop is that you may not
change the collection being walked; `delcurs` and `oncecurs` exist because
removal is the common case where that rule bites.

The table above names what each cursor walks, which is the part that
belongs to the reftype.  The authoritative list of which cursors are
default and which are on demand is regenerated from the database in
[dmmeta.fcurs](/txt/ssimdb/dmmeta/README.md#dmmeta-fcurs), and the cursor types
themselves are [amcdb.curstype](/txt/ssimdb/amcdb/README.md).

### Allocators
<a href="#allocators"></a>

Pools that own memory and hand out records.  A pool is either a
**base pool** (talks to the kernel) or chains to another pool via
`dmmeta.basepool`.  See [Memory Pools](/txt/exe/amc/pool.md) for
the overall allocator model.

|Reftype|One-line description|
|---|---|
|[Malloc](/txt/exe/amc/reftype/Malloc.md)|Pass-through for libc `malloc` / `free` — base pool|
|[Sbrk](/txt/exe/amc/reftype/Sbrk.md)|Bump-pointer allocator via `sbrk` / huge pages — base pool|
|[Tpool](/txt/exe/amc/reftype/Tpool.md)|Singly-linked freelist; fixed-size, very fast, no return-to-OS|
|[Lpool](/txt/exe/amc/reftype/Lpool.md)|36 Tpools, one per power-of-2 size class — varlen allocator|
|[Blkpool](/txt/exe/amc/reftype/Blkpool.md)|Block allocator with refcount, suitable for FIFO message buffers|
|[Lary](/txt/exe/amc/reftype/Lary.md)|Level array (36 doubling blocks) — append-only with permanent pointers|
|[Delptr](/txt/exe/amc/reftype/Delptr.md)|Lazy single-element allocator — like Val but starts NULL|
